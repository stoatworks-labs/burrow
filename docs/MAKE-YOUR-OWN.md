# Make your own

Burrow is not really about these plugins. Underneath the names it is a desktop
installer for **software published as GitHub releases**: it reads one JSON file
listing what exists, works out what you already have, downloads the right archive
for your platform and architecture, and puts each payload where its host looks for
it — asking for a password only where the destination genuinely needs one.

If that is how you ship, this repository is a working starting point. Fork it,
write your own catalogue, and it installs your software instead.

> **Nobody has done this yet.** The seams described below are real seams — the
> catalogue is genuinely an interface, and the fleet-specific facts really are in
> the handful of places named here — but they have only ever been exercised by the
> fleet that owns them. Expect to read Rust, and expect at least one thing that is
> hardcoded in a spot this page has not thought of. If you find one, a pull request
> improving this page is welcome.

## What Burrow assumes about you

Four things, and if any of them is false you are looking at a bigger job than a
fork:

- **Your releases are on GitHub, and public.** Downloads are restricted to a
  compiled-in list of hosts (`src-tauri/src/net.rs`), no credentials are sent, and
  nothing authenticates.
- **Your artefacts are archives.** `.zip` for everything except Companion modules
  (`npm pack` tarballs) and macOS applications, which may also arrive as a `.dmg`.
- **You can serve one JSON file over HTTPS.** Anything that can host a static file
  will do — including GitHub Pages, or a release asset.
- **What you install is a bundle, an application, or a file with a known
  extension.** Burrow places named payloads out of an archive; it does not run
  installers and it does not execute anything it downloads.

## 1. The catalogue is the whole interface

Everything the app knows about your software comes from one file. Burrow's own
lives at `stoatworks-labs.com/catalog.json` and is generated by a separate website
repository at build time; nothing about that arrangement is required. A hand-written
file works. So does a GitHub Action that walks your releases and commits the result.

The smallest catalogue that loads is the one in the parser's own tests
([`crates/burrow-core/src/catalog.rs`](../crates/burrow-core/src/catalog.rs)):

```json
{
  "schema": 1,
  "generated": "2026-08-24T20:00:00Z",
  "formats": { "ffgl": { "label": "FFGL", "hosts": "Resolume" } },
  "entries": [{
    "slug": "tinsel", "name": "Tinsel", "repo": "tinsel", "kind": "plugin",
    "version": "v1.0.2",
    "builds": {
      "ffgl": { "macos": { "url": "https://example/t.zip", "size": 1, "arch": "universal" } }
    },
    "notes": [{ "tag": "v1.0.2", "kind": "commits", "lines": ["did a thing"], "filtered": 4 }]
  }]
}
```

Anything marked `#[serde(default)]` on `Entry` may be left out entirely. What each
field is for is documented on the struct, but the ones worth knowing before you
start:

| Field | What it does |
|---|---|
| `slug` | The identity of the thing, everywhere: settings keys, the ledger, the demo folder, the thumbnail filename. Do not change one after release. |
| `kind` | `plugin`, `app` or `companion`. A kind this build does not manage is kept and never offered. |
| `category` | Which tab it appears under. Absent means `video`, for historical reasons — say it explicitly. |
| `parent` | Set on a thing that only exists to serve another (Companion modules). The UI nests it under that slug instead of listing it as a peer. |
| `status` | An id into the catalogue's own `statuses` map. Yours can say whatever you like. |
| `entries` | **The names the archive unpacks to that a host actually loads.** This is what lets Burrow recognise a copy somebody installed by hand and remove exactly the right files later. |
| `extras` | Everything else in the archive — documentation, samples, a command-line helper. These must not land in a plugin folder, and must not be recorded as yours, or a later uninstall deletes files that may not be. |

`formats`, `categories` and `statuses` at the top level are **vocabularies sent
alongside the ids**, so that a catalogue can gain a format, a category or a status
and have it appear correctly labelled in a copy of the app nobody has updated. Keep
that property. It is the reason a deploy cannot brick clients in the field — and
this project has already had one deploy that did, before the rule existed.

⚠️ **`assets` is additive beside `builds`, never inside it.** `builds` is
format → platform → one asset, which cannot express separate arm64 and x64 builds.
The flat, architecture-aware `assets` list sits *beside* it, is preferred where
present, and is ignored by anything that has never heard of it. Adding a third level
of nesting inside `builds` would change the shape of a field shipped clients already
parse. Do not.

`versions` is the rollback list — thinner on purpose (tag, url, size), because
Burrow reads the real payload names out of the archive as it installs rather than
assuming an old release had the same bundles.

### The copy that ships inside the app

`src-tauri/assets/catalog.json` is baked into the bundle and does three jobs, none
of them optional:

1. a first run with no network still shows everything you publish;
2. it is the baseline that stops "What's new" announcing your entire catalogue as
   new on first launch;
3. it is the only thing that knows which projects exist when the live list cannot
   be reached.

The release workflow refuses to build without it, and refuses a catalogue with zero
entries — a catalogue that parses but is empty would silently tell every copy of the
app that your software had ceased to exist.

## 2. Point the app at your list

Three places, and missing the second is the one that fails confusingly — the list
loads, and every download is refused.

| Where | What to change |
|---|---|
| [`src-tauri/src/settings.rs`](../src-tauri/src/settings.rs) | `DEFAULT_CATALOG_URL` — the compiled-in default. |
| [`src-tauri/src/net.rs`](../src-tauri/src/net.rs) | `REDIRECT_HOSTS` — an allowlist, so a compromised or mistyped catalogue cannot turn an install into a fetch from anywhere at all. Add your host; drop `stoatworks-labs.com`. |
| [`src-tauri/tauri.conf.json`](../src-tauri/tauri.conf.json) | `connect-src` in the CSP, if you keep the feedback intake or add any other endpoint. |
| [`src-tauri/tauri.conf.json`](../src-tauri/tauri.conf.json) | `plugins.updater` — the endpoint the app updates *itself* from, and the public key it verifies against. Both are this project's. See §8; if you do not want a self-updater, delete the block, the `tauri-plugin-updater` dependency, `src-tauri/src/update.rs` and the two components that use it. |

The URL is stored per user in `settings.json` in the app's config directory
(`~/Library/Application Support/<bundle identifier>/settings.json` on macOS). Editing
`catalogUrl` there is the quickest way to try a catalogue without rebuilding — the
Settings tab shows the URL but does not let you type one, deliberately.

## 3. Recognising your own files

**Change `OWNED_PREFIXES` in
[`crates/burrow-core/src/bundleinfo.rs`](../crates/burrow-core/src/bundleinfo.rs)
before you wonder why nothing installs.**

On macOS, Burrow reads `CFBundleIdentifier` out of an installed bundle to decide
whether it put it there. A bundle whose identifier does not start with one of those
prefixes is reported as *foreign*: not adopted, not counted as installed, and never
replaced or deleted. That is the correct behaviour — it is what stops the app
deleting somebody else's plugin that happens to share a name — but if you leave the
Stoatworks prefixes in place, **your own payloads are the foreign ones**.

Filename is the primary check (the catalogue declares the names); the identifier is
the second one. Windows payloads carry no identifier at all, so "unknown" is a normal
answer there and the ledger and the file hashes do the work instead. The reconciliation
logic is in [`crates/burrow-core/src/ledger.rs`](../crates/burrow-core/src/ledger.rs),
and you can point it at your own machine without building the GUI:

```bash
cargo run -p burrow-core --example scan -- path/to/catalog.json
```

It reads, and writes nothing.

## 4. Formats, categories and destinations

A **format** is really "which host family loads this", and it decides where a payload
goes and whether that needs a password. The vocabulary is the `Format` enum in
[`crates/burrow-core/src/model.rs`](../crates/burrow-core/src/model.rs), and adding
or removing one means touching four things on it:

- `SHIPPING` — the single switch for what is actually offered. A format that is
  representable but not shipping is parsed, filed and never installed, which is how
  you stage one before its first release exists.
- `payload_extensions` — the suffixes that identify a payload inside an archive.
  This is what picks the `.vst3` out of a zip that also holds a `.component`, a
  standalone app and a README, with no probe having told it the names.
- `payload_is_whole_archive` — for the cases where the archive *is* the thing: a
  Companion module (an npm tarball with no suffix to recognise) and a Windows
  application (a folder whose `.exe` is useless without the DLLs beside it).
- `needs_elevation` — see §5. Adding a format here is a security decision, not a
  plumbing one.

**Where each one goes** is [`crates/burrow-core/src/dest.rs`](../crates/burrow-core/src/dest.rs),
one function per destination, per platform, with the evidence for each path in a
comment above it. Detection returns nothing rather than guessing, so an empty result
means "not found" and never "look somewhere plausible". If your software goes
somewhere else entirely, this is the file you rewrite.

**Categories are tabs.** They exist in three places, and all three need to agree:
`Category` (plus `SHOWN`) in `model.rs`, `CategoryId` in
[`src/api/types.ts`](../src/api/types.ts), and `CATEGORY_TABS` in
[`src/App.tsx`](../src/App.tsx). The *labels* come from the catalogue, so renaming a
tab needs no rebuild; adding one does. The Firmware tab is a deliberate empty
placeholder that says so — [`src/tabs/Firmware.tsx`](../src/tabs/Firmware.tsx) is the
first thing to delete if you do not want it.

If you ship applications and nothing else, the honest fork is small: keep
`Format::App`, delete the rest, and you keep the download, verification,
de-quarantine, ledger and rollback machinery without any of the plugin-specific
parts.

## 5. If nothing you install needs a password, delete the helper

Two of Burrow's seven formats install into root-owned directories that have no
user-writable alternative any host looks in. That is the only reason `burrow-helper`
exists, and if your destinations are all inside the user's own home directory you
should remove it: drop the crate, the `externalBin` entry in `tauri.conf.json`, and
[`src-tauri/src/elevate.rs`](../src-tauri/src/elevate.rs).

If you do need it, the rules in
[`crates/burrow-plan/src/lib.rs`](../crates/burrow-plan/src/lib.rs) are the security
statement and they are load-bearing:

- Every destination must be a **direct child, exactly one component deep**, of a
  compiled-in root in `WHITELIST`. Not a descendant — a child.
- The whitelist is a `const`. It is not read from settings, not passed in the plan,
  and not derived from an environment variable, because each of those is something
  an attacker who can write one file gets to influence. A user-configured custom
  destination is **never** elevated.
- The operation set (`ensure_root`, `replace`, `retire`, `purge`) is chosen so that
  "delete an arbitrary path as root" is not expressible. `purge` refuses anything
  whose name does not end in the current plan's random nonce — you can only delete
  what you just renamed, moments earlier, in the same operation.
- Its dependency list is `burrow-plan`, `serde` and `libc`. No HTTP client, no
  archive decoder. If anything else appears there, something has gone wrong.

There are tests for every one of those refusals. Add to them before you change
anything in that crate — and note the standing rule that adding a *format* must not
add an elevated path (`no_format_added_for_the_new_categories_can_ask_for_a_password`
pins it).

Windows has no privileged helper at all. It is not written, and the app refuses those
installs with an explanation rather than half-working.

## 6. Naming it yours

| File | What is in it |
|---|---|
| [`src-tauri/tauri.conf.json`](../src-tauri/tauri.conf.json) | `productName`, `identifier`, the window title, the CSP, the icon list. The identifier decides where settings, the ledger and the cache live. |
| `src-tauri/icons/`, `app-icon.png` | The icons. Regenerate with `npm run tauri icon`. |
| [`src/App.tsx`](../src/App.tsx) | The `<h1>`. |
| [`src/tabs/Settings.tsx`](../src/tabs/Settings.tsx) | The "what this app sends" paragraph, which names the host out loud. If you change what it sends, change this first. |
| [`src-tauri/src/net.rs`](../src-tauri/src/net.rs) | `user_agent()` — the only thing about the caller that leaves the machine. |
| `package.json`, `Cargo.toml`, the crate names | `burrow-core`, `burrow-plan`, `burrow-helper`. Renaming these is optional and touches every import. |
| [`.github/workflows/release.yml`](../.github/workflows/release.yml) | The product name and bundle identifier are repeated in the packaging step. |
| `README.md`, `LICENSE`, `ATTRIBUTIONS.md` | MIT — keep the copyright notice and the attributions, and add your own. |

## 7. What ships inside the app

Two destinations, and Tauri treats them differently. Getting it wrong ships an app
with no pictures and nothing failing loudly:

- `src-tauri/assets/` is a bundle **resource** — on disk inside the app, readable
  from Rust, served by the loopback demo server. The baked catalogue and the demos
  live here.
- `public/` is a **frontend** asset, bundled into `dist` and addressed from the UI as
  `./thumbs/x.png`. The images have to be here.

[`scripts/sync-assets.sh`](../scripts/sync-assets.sh) gathers all of it, and is the
most fleet-shaped script in the repository: it reads a sibling website checkout and a
directory of plugin repositories at fixed paths. **A fork replaces it.** The minimum
it has to produce is `src-tauri/assets/catalog.json`, one `public/thumbs/<slug>.png`
per entry, and the compiled helper in `src-tauri/bin/` if you kept it. A missing
image degrades to the project card and then to nothing, rather than to a broken-image
box, so this fails gently.

The bundled browser demos (`src-tauri/assets/demos/`) and the in-window video player
are entirely optional. Both exist to keep one specific promise — that the app talks
to the catalogue host and GitHub and nothing else, no YouTube embeds and no third-party
thumbnails. If you do not need that promise, deleting
[`src/components/VideoModal.tsx`](../src/components/VideoModal.tsx),
[`src-tauri/src/demos.rs`](../src-tauri/src/demos.rs) and the demo assets removes a
lot of surface. If you keep the demo server, keep the `connect-src 'none'` it sends:
a demo that can make network requests is a different thing entirely.

## 8. Building and releasing

```bash
npm install
npm run tauri dev
cargo test --workspace
```

For a real bundle, [`scripts/build-app.sh`](../scripts/build-app.sh) exists because
of one trap worth inheriting: `tauri build` signs the bundle *before* the bundler
places `Contents/Resources/`, so the signature does not cover the catalogue or the
demos. A locally built copy still launches — Gatekeeper only assesses quarantined
bundles — so the failure first appears on somebody else's machine, after a download.
The script re-signs afterwards, nested binaries first, which is the order `codesign`
requires.

[`scripts/release-lib.sh`](../scripts/release-lib.sh) turns a staging directory into
the artefacts: `.dmg` and `.pkg` on macOS, NSIS `.exe` and a portable `.zip` on
Windows, `.tar.gz` on Linux. macOS bundles are Developer ID-signed and notarised when
the `RL_MAC_*` / `RL_NOTARY_PROFILE` variables are set, and fall back to ad-hoc
signing when they are not — which still needs the documented
`xattr -dr com.apple.quarantine` step on the user's machine. Windows artefacts are
Authenticode-signed when the `RL_SIGN_*` variables are set and skip rather than fail
when they are not. The workflow in this repository carries no signing secrets, so
what it publishes is the ad-hoc path.

**The self-updater needs a key of your own before it needs anything else.**
`tauri signer generate` makes a minisign pair; the public half goes in
`tauri.conf.json` and is compiled into every build, the private half into the
repository secret `TAURI_SIGNING_PRIVATE_KEY`. The release workflow signs each
platform's update artefact with it and publishes `latest.json` beside them
([`scripts/make-latest-json.mjs`](../scripts/make-latest-json.mjs)).

Two things about that are worth copying rather than rediscovering. The macOS
tarball is built from the **re-signed** bundle rather than by Tauri's
`createUpdaterArtifacts`, which would package the stale signature the paragraph
above is about — invisible until a user updates rather than downloads. And the
manifest generator **fails the release** when any platform's artefact is
missing, because a manifest with one platform absent makes every copy on that
platform report an error about *your* release, at every check, until somebody
tells you.

And keep the private key. Installed copies verify against the public half they
were built with, so losing it means nobody already out there can ever be updated
again.

The `<!-- downloads:start -->` block in the README is written by a fleet tool that is
not in this repository. Either write that section by hand or drop the markers.

## 9. A checklist

- [ ] Catalogue written, served over HTTPS, and a copy committed at `src-tauri/assets/catalog.json`
- [ ] `DEFAULT_CATALOG_URL` and `REDIRECT_HOSTS` point at your host
- [ ] `OWNED_PREFIXES` names your bundle identifiers
- [ ] Formats trimmed to what you ship (`Format::SHIPPING`) and destinations checked in `dest.rs`
- [ ] Categories agreed across `model.rs`, `types.ts` and `App.tsx`
- [ ] Helper deleted, or its whitelist reviewed and its tests updated
- [ ] Product name, bundle identifier, icons and user-agent are yours
- [ ] `cargo test --workspace` and `(cd src-tauri && cargo test)` pass on all three platforms in CI
- [ ] Updater endpoint and public key are yours, the signing secret is set, and the block is deleted if you do not want one
- [ ] Install and uninstall exercised against a temporary directory before a real one

One more, from this project's own experience: **say what you have actually verified**,
in the README and in the app, and say it in the same words. An installer that
overstates what it has been tested against is worse than one that has not been tested
at all, because somebody trusts it mid-show-week.
