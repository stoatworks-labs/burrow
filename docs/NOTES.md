# Notes

Working notes for this repo: status, decisions, and the traps that have actually
bitten. Written in the first person and dated by when each thing was learned —
that date is usually the useful part. Cross-cutting fleet knowledge lives in
[fleet-notes](https://github.com/stoatworks-labs/fleet-notes).

*Stoatworks Burrow — the optional desktop client for the fleet's video plugins.*

## 2026-08-24 — first build

Built in one pass. The catalogue, the two library crates, the privileged helper,
the Tauri shell and the UI all exist and are exercised; nothing has been installed
into a live host yet.

**The catalogue is an Astro route, not a script.** The obvious design was a Python
generator writing `plugins.json` into the website's `public/`. The website already
generates `releases.xml` and `llms.txt` from its own data at build time, and
`llms.txt.ts` argues the case in a comment — a hand-written version is accurate on
the day it is written and quietly wrong a month later. Same reasoning applies, and
it means the catalogue cannot drift from the download tables because they are the
same source.

**Two plugins would have vanished silently.** `downloads.json` marks assets
`stable` when their URL is the unversioned `/releases/latest/download/` alias. The
obvious rule — only take stable ones — drops **amber and cartridge**, which publish
only versioned archives. Nothing would have reported it. The catalogue now prefers
the alias and falls back to a pinned URL marked `pinned: true`, which is exact
rather than stale because the file is regenerated at every release anyway.

**"Copy every top-level entry" is wrong for a quarter of the fleet.** Probing all
77 archives found four carrying more than plugins: burin's `example-plate.svg`,
flipbook's `example-sheet.png`, gridiron's `demo logos/`, and cartridge's `LICENSE`,
`README.md`, `docs/` and `cartridge-helper`. Copied wholesale they land in the
user's Resolume folder — and worse, Burrow would record a `LICENSE` as its own and
delete it at uninstall. `cartridge-helper` is a real and useful binary, but it is a
command-line program the user runs, not something Resolume loads.

**Archive contents are read without downloading them.** A zip's central directory
is at the end of the file, so `zipfile` over an HTTP-range file object gets the
entry names for about 1.8 KB of a 624 KB archive. All 77 cost 62 KB.

**Luma Keyer uses a different bundle identifier.** Surveying the 22 bundles
installed here: twenty-one are `com.stoatworks.*` and `LumaKey.bundle` is
`com.allansargeant.ffgl.lumakey`. It is the oldest plugin and predates the
convention. Burrow accepts both prefixes deliberately — an already-installed bundle
keeps its shipped identifier forever, so recognising only the new one would make
every existing Luma Keyer install permanently invisible. Whether the fleet
normalises it is a separate question, filed separately.

⚠️ **The `OFX_*_Example` bundles are `com.stoatworks.ffgl.ofx.*`.** They were
generated by resolume-ofx-bridge from the OFX SDK samples, so the identifier prefix
does *not* exclude them. They are invisible to Burrow because their **names** are
not declared by any catalogue entry. The name check is doing the real work; the
identifier is the secondary guard. Do not reverse that.

**`sync-support-footer.sh`'s TARGETS list is not comment-aware.** A `#` line inside
the here-string is read as a repo name and reported as a missing checkout. Notes go
above the assignment.

**The demo server sends `connect-src 'none'`.** The bundled demos vendor the shared
support footer, which posts feedback to the intake endpoint. That is right on the
hosted copies and wrong here — this app has its own footer, and "the demos never
phone home" should be a property of the server rather than a hope about the
vendored script's own origin checks.

## 2026-08-24 — the first local .app

**`tauri build` leaves the bundle's signature stale.** It signs ad-hoc, and
*then* the bundler places `Contents/Resources/assets/` — the catalogue, demos and
thumbnails — which the signature does not cover. `codesign --verify` reports
"code has no resources but signature indicates they must be present".

A local build still launches, because Gatekeeper only assesses bundles carrying
the quarantine attribute and a locally built one has none. That is what makes it
dangerous: it would first fail on somebody else's machine, after a download.
`scripts/build-app.sh` re-signs afterwards — nested binaries first, then the
bundle, which is the order codesign requires and the order rl_adhoc_sign uses.

⚠️ **An `externalBin` sidecar goes in `Contents/MacOS/`, not `Contents/Resources/`.**
The first version of `helper_path()` looked in the resource directory, which is
where the catalogue and demos go but not where Tauri puts sidecars. That is not a
compile error and not a startup error: the app runs perfectly until somebody
installs an OpenFX plugin, and then fails at the moment it asks for a password.
It now checks beside the executable, then Resources, then the workspace's own
`target/` so elevation is testable under `tauri dev` with no bundle at all.

**First launch, verified:** the app starts, falls back to the baked catalogue
(the website route is not deployed yet, so the URL 404s), writes settings, and
seeds all 24 entries into `seen` — which is what stops "What's new" announcing
the entire fleet on a first run.

## 2026-08-24 — no Linux build, deliberately

Burrow's bundle targets are macOS and Windows only for v0.1.0.

DaVinci Resolve does run on Linux, and OFX has a real home there —
`/usr/OFX/Plugins`, with a `Contents/Linux-x86-64` arch directory, both of which
the OpenFX reference host looks for. So a Linux Burrow is not a silly idea.

It is just useless today: **no plugin in the fleet ships a Linux artefact.** All
24 are macOS + Windows. A Linux Burrow would detect the destination correctly and
then offer nothing at all.

The plugin side is close, though — every plugin's `CMakeLists.txt` already has a
`Contents/Linux-x86-64` branch for the OFX target. What is missing is a Linux row
in each release workflow, and `libglew-dev` on the runner (GLEW arrives through
the vcpkg manifest today, which is a Windows path). A Linux FFGL build would be
pointless in the same breath — Resolume is macOS and Windows only — so a Linux
job should build OFX alone.

Add the Linux target here the same week the first plugin ships one, not before.

## Still open

- Nothing has been installed into a running Resolume, Resolve or After Effects
  through the finished app. The install path is verified against temporary
  directories and against real release archives, but the last step is untested.
- The macOS authorisation prompt has never been driven end to end.
- Quarantine clearing cannot be proven from a local build — it needs a downloaded,
  Gatekeeper-quarantined copy of Burrow itself. That is precisely why the clearing
  is unconditional.
- **Windows has no privileged helper.** OpenFX and Adobe installs there are refused
  with an explanation rather than half-working. FFGL is unaffected. It needs a
  UAC-manifested binary and an owner-SID provenance check in place of the uid
  comparison.
- No CI, no release workflow, no user guide yet.
